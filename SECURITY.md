# Security

Report vulnerabilities at https://github.com/urwid/urwid/security/advisories

## Threat model

### Web display (`urwid.display.web`)

The web display runs an urwid application as a CGI script.
The first request of a browser starts the application,
and later requests of the same browser carry the session id in the `X-Urwid-ID` header
to send keystrokes (`handle_short_request()`) or to fetch screen updates in the polling mode.

What the module protects:

- Session files
  - The input pipe, the polling update socket and the polling daemon's error log of every session
    live in the directory `urwid-web-<uid>` under the `pipe_dir` given to `set_preferences()`.
  - The module creates that directory with mode `0700` and refuses to run when it is not a directory
    owned by the effective user, or when the group or other users have any access to it.
  - The files are named after a hash of the session id, so a listing of the directory does not reveal the id.
  - The polling daemon creates its files with umask `077`.
- Session id
  - The id is generated by `secrets.token_urlsafe()`.
  - A client-supplied id is checked against `_URWID_ID_MAX_LEN` and `_URWID_ID_CHARS` before any file lookup.
- Resource limits
  - A keystroke request is read up to `MAX_READ` bytes.
  - The screen size is capped at `MAX_COLS` and `MAX_ROWS`.
  - The number of concurrent sessions of one user and `pipe_dir` is limited to about `max_clients`
    (`set_preferences()`): two sessions starting at once can both pass the check, and stale pipes count towards it.

What the deployment has to provide:

- The session id is a bearer credential.
  Anyone who sends it to the CGI endpoint can read the screen and send keystrokes to the session.
  Keeping it secret in transit is the web server's job: serve the script over HTTPS only.
- The module does not authenticate users.
  The web server decides who may reach the CGI script, for example with HTTP authentication.
- Processes that run as the same user as the CGI script are trusted, because they can open the session directory.
- Other users must not be able to rename entries in `pipe_dir`:
  it is either private to the user or a sticky directory such as `/tmp`.
  In a shared `pipe_dir` such as `/tmp`, another local user can create `urwid-web-<uid>` first,
  and the display then refuses to run for that uid.
  A `pipe_dir` private to the user avoids this.

Reports that need one of these conditions to be broken are not treated as vulnerabilities of urwid.

For production use, build a display module on a maintained HTTP and WebSocket library such as aiohttp or Tornado,
which provide TLS, authentication and connection handling.
